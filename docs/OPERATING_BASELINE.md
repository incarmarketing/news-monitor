# 인카 모니터링 시스템 운영 기준

이 문서는 개선점 검토 때 이미 반영된 항목을 다시 신규 개선점으로 제안하지 않기 위한 현재 기준표입니다.

## 알림과 감시

- 기본 부정기사 감시 주기: 24시간, 10분 기준
- 기본 검사 범위: `minutes_back=10`
- 부정기사 감시 workflow: `.github/workflows/negative-watch.yml`
- 주 스케줄러: cron-job.org 10분 주기
- 복구 스케줄러: Supabase Cron은 매시 05, 15, 25, 35, 45, 55분에 확인
- 부정기사 감시 복구: 마지막 정상 완료가 25분 이상 없을 때만 재호출
- 보고서 복구: cron-job.org 정시 호출과 GitHub 15분 예비 호출을 기다린 뒤 40분부터 최종 복구
- 재요청 잠금: GitHub가 보고서 작업을 접수하면 최소 30분 동안 중복 요청 금지
- GitHub Actions 자체 감시 예약: 사용하지 않음
- 감시 실행 코드: `negative_watch.py`
- 감시 로그 테이블: `negative_watch_runs`
- 최신 운영 문구: `10분 주기`, `검사 10분`

## 주가 수집

- 당사와 KOSPI/KOSDAQ 지수: 장중 매분 수집
- 비교 종목: 3개 묶음으로 나눠 종목별 약 3분 주기 수집
- 외부 API 요청 간격: 1.1초, 요청 제한시간 8초
- 10분 이상 끝나지 않은 실행: 다음 실행이 실패로 마감 처리
- 목적: 24개 종목 전체를 매분 직렬 호출하면서 발생하던 API 초당 한도와 55초 타임아웃 방지

## 발송 채널

- 기본 발송 채널: Slack
- 발송 이력 테이블: `notification_sends`
- Kakao 발송 코드는 삭제하지 않고 `legacy/kakao/`에 격리

## 보고서 구조

- 프론트 리포트 UI: `frontend/src/reportComponents.jsx`
- 리포트 계산 모델: `frontend/src/reportModel.js`
- 리포트 전용 스타일: `frontend/src/report.css`
- PDF 저장은 프린터 대화상자 대신 `reportPdf.js`에서 가로 A4 파일을 직접 생성한다. 본문 여백은 10mm, 한글은 임베드 글꼴, 기사 링크와 선택 가능한 텍스트를 유지한다.
- PDF 엔진과 정적 글꼴은 저장 버튼을 누를 때만 불러온다. 기존 수동 인쇄 스타일과 모바일 리포트 숨김 정책은 유지한다.

## 언론사 분석과 기사 식별

- 언론사 상세의 기본 보기는 최근 30일 보도 분석이며 90일로 전환할 수 있다. 기존 누적 기사·기자 이력은 별도 탭으로 유지한다.
- 분석은 기간 전체 모니터링 데이터로 집계한다. 페이지의 30건으로 전체를 추정하지 않는다. 조회가 실패하거나 20,000건 상한으로 완전한 조회가 불가능하면 0건 통계로 대체하지 않는다.
- 논조와 주분류의 각각의 합계는 기간 전체 건수와 일치해야 한다. 당사 언급과 당사를 직접 대상으로 한 부정 보도를 별도로 집계하며, 후자는 명시적인 `negativeTarget=own` 근거가 있어야 한다.
- 기간 데이터는 기존 공유 캐시(2분)를 재사용하고, 상세 진입·기간 변경·수동 갱신 때만 조회한다. 조회 중에는 상세 갱신 중복 클릭을 막는다.
- 구글·포털과 원문의 전체 제목이 같고 같은 언론사·날짜이며 원문 후보가 하나면 원문을 우선 표시한다.
- 한쪽 제목이 잘렸다면 같은 발행 분, 30자 이상 의미 문자로 된 긴 제목 앞부분, 단 하나의 원문 후보를 추가로 요구한다. 후속 기사 제목이나 원문 ID가 모호하면 합치지 않는다.
- 통합 표시는 원문 링크·원문 식별자와 전체 제목을 사용한다. 이전 포털 링크·해시는 별칭으로 보존한다. DB 원본 행을 삭제하거나 알림을 재발송하는 처리가 아니다.
- 캐시된 정규화 기사도 당사 언급, 부정 대상, 클리핑 근거와 발행 시각을 다시 읽을 때 잃지 않아야 한다.
- 배포 후 Design QA에서 직접 PDF 다운로드·실패 후 재시도와 언론사 분석·관리 화면의 PC/모바일 정렬을 자동 검사한다.

## 점검 원칙

- 개선점 보고 시 `이미 반영된 기준`, `남은 결함`, `신규 제안`을 분리한다.
- 단순 잔존 문구 정리는 신규 기능 개선으로 보고하지 않는다.
- 운영 기준과 충돌하는 문구는 코드 검색으로 먼저 확인한다.
